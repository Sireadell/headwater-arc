Honesty table

What is real, what is limited, and what is not built. Plain statements, checkable in the code, not buried in comments.

Real
ERC-8004 registry reads
Calls the live Identity and Reputation registries on Arc mainnet (0x8004A169…, 0x8004BAa1…). Every agent id the registry holds is read, and every review event is saved with the wallet that sent it.
USDC payments
On Arc, USDC is the coin that pays fees, so a plain send leaves no ordinary token log. Arc’s system address writes one log for every USDC move, valued with 18 digits instead of 6. Headwater reads those logs and divides by 1012. Checked against live receipts.
Hand-checked findings
Agent 346 and agent 8 were checked against the chain’s own receipts: sender, receiver and amount matched. A separate tester rebuilt the whole audit from a fresh copy and got identical results for all 116 agents, then re-checked 13 funding payments against receipts.
Records on Arc
Findings are written to Arc mainnet as small transactions carrying readable text. Open one on the explorer, click “View details”, and switch the data to UTF-8.
Same rules as the Monad build
The verdict rules are a port of the ones in the Monad version of Headwater, and the 29 tests that cover them were carried over and pass unchanged. Only the data source differs: a saved list of Arc payments instead of an indexer.
Seven signals under each verdict
Owner funded other agents’ reviewers, cross-agent review overlap, circular funding, funder fan-out, shared funding source, wallets created together, and automated review timing. Context only: each says what it saw and never changes a verdict by itself.
Limited, and disclosed
Two funding hops
Owner to reviewer, and owner to one wallet to reviewer. A longer chain is not followed, so absence of a link is weaker evidence than a link.
Window starts at block 10,000,000
Payments before that are not in view. The payment log is empty in the first 5,000,000 blocks and nearly empty around 10,000,000, so little is lost, but I can’t prove nothing earlier matters.
Reviewers with no funder found
Four reviewers have no funding payment in the window. They show no link either way, and the verdicts say how many reviewers of each agent have a funding record.
Busy wallets are set aside
Nine wallets with thousands of payments (exchanges, bridges, faucets) are ignored as funders, because being paid by one links you to nobody. The agent’s own owner is never set aside, so an owner that happens to be busy still counts.
Small top-ups count
A small payment from an owner to a reviewer is counted, and marked as a top-up on the lookup page. Many such links look like a developer funding a test wallet to pay fees. Read the amount.
Payment timing
“Paid before rating” compares the payer’s first payment to the owner against the payer’s first review. A later payment by an already-paying wallet is not timed separately. Times are block numbers, about two a second.
Code check is a sample
Up to 40 reviewers per agent are checked for contract code. The sample size is stated on every verdict.
Review rings the check cannot see
Owners that review each other’s agents in a loop are not detected when a busy wallet funded all of them. A hand test found one such loop (agents 1407 to 1411). The big reviewer 0x6a663f also reviews agent 228 while the owner of that agent reviews agent 211, which it owns.
My own wallet
The wallet that wrote the records on Arc (0xb3FB…2B53) left one review, on agent 192, and was also the first to send money to agent 192’s owner. The lookup page for agent 192 shows exactly what that does to its verdict.
Snapshot, not live
Verdicts are rebuilt by hand from saved data. Only the newest-ratings feed on the home page reads Arc live.
Not built
Wallet reputation labels
No outside label service is used. Headwater reads the chain only.
Automatic refresh
The audit is rerun by hand with the scripts in the README. A scheduled rebuild is the next step.
Automatic records
New findings are written to Arc by hand, because doing it automatically would need a wallet key on a server.
What the verdicts mean
NO EVIDENCE
Never rated. Nothing to trust or distrust.
THIN
Every rating came from one address. One address agreeing with itself is one opinion, however many times it is recorded.
SELF REVIEWED
The owner’s wallet is among the raters, or the owner sent and paid for a review that carries another wallet’s name. Comparing addresses misses that; the transaction shows who really sent it.
APP GENERATED
Most raters are application contracts recording outcomes (for example a game’s winner and loser). That is the standard working, not a warning, but it is not customers vouching for the agent.
OWNER FUNDED
The agent’s own owner paid for its raters, directly or through one wallet. Not an accusation: a paid campaign can be legitimate. It means much of the score is not independent evidence.
ROUND TRIP
The owner paid the raters, and the same wallets sent money back to the owner after rating. Ranked above OWNER FUNDED because it says more, and below APP GENERATED because an application returning a balance is ordinary.
RING
The agent’s raters trace to one money source, or one reviewer, that also sits behind several other agents. Each agent looks ordinary alone. A shared funder only counts where the wallets it funded are at least half of that agent’s raters.
NO LINK FOUND
More than one reviewer, and no funding link across two hops. Weaker evidence than a link.
Callable by an agent, not just readable by a person
JSON API
api/index.json lists every rated agent. api/agents/346.json is one full report. api/rings.json lists the groups. No key, no server. An agent id with no file has never been rated.
MCP server
mcp/server.mjs lets an AI agent ask “what is this agent’s reputation made of?” before it pays or trusts another agent. See the README for the one-line setup.
